## 一、先说结论：你原来的写法为什么不行

原来写的是「在线教育平台开发」，实际交付物是一个 **Java Swing 桌面程序** + 一个 **纯静态假 Demo**。
两个硬伤：

1. **HR 打不开**。Swing 桌面程序没法用链接演示，HR 只能看文字描述 —— 而文字谁都会写。
2. **假 Demo 是负分**。`edusystem-demo.surge.sh` 是纯静态页面，数据全写死在浏览器里，一个网络请求都没有。面试官按 F12 看 Network 面板，0 个请求，你的「在线教育平台」当场变成诚信问题。

现在改造后：**后端真在跑、数据库真有数据、前端每个操作都是真实 HTTP 请求、Agent 真的在调你的业务接口**。这才是「可验证」。

## 二、简历正文（直接抄，把【】里的内容换成你自己的）

> 建议放在「项目经历」第一位。标题不要写「在线教育平台开发」这种听起来像培训班作业的名字。

### 高校教务与学情分析平台（含 LLM 智能体）｜个人独立开发｜2026.08 – 2026.09

**技术栈**：Java 21 / Spring Boot 3.5 / Spring Security + JWT / Spring Data JPA / MySQL + H2 / Maven / Docker / GitHub Actions

- 独立设计并实现前后端一体的教务平台，覆盖**用户、课程、选课、作业、提交、评分、知识点** 7 个业务域，对外提供 **32 个 REST 接口**；基于 Spring Security + JWT 做无状态认证，密码使用 BCrypt 加盐哈希存储，并按 student / teacher / admin 三种角色做**接口级权限隔离**（越权访问返回 403，未认证返回 401）。
- **解决选课高并发下的超卖问题**：选课链路采用数据库悲观写锁（`SELECT ... FOR UPDATE`）+ 事务 + 回滚，在行锁内完成「查重 → 容量校验 → 写入选课记录 → 维护冗余计数」；编写 50 线程并发压测，容量 20 的课程实测**成功 20、被拒 30、超卖 0 次、异常 0 次**，选课记录行数与计数完全一致。
- **定位并优化 N+1 查询**：作业完成度统计原实现在 30 名学生 × 4 次作业的数据集上产生 **122 条 SQL**；改用一条 `GROUP BY` 聚合查询后降至 **2 条**，SQL 条数 **122 → 2（减少 120 条）**，平均响应从百毫秒级降到个毫秒级。通过自定义 Hibernate `StatementInspector` 统计真实 SQL 条数，使优化前后有可复现的量化依据，并用测试断言两种实现统计结果语义一致。
- **独立设计 LLM 智能体模块**：基于 Function Calling 定义 **12 个只读业务工具**（覆盖课程、作业、成绩、知识点、学情统计、平台概览等，按学生/教师/管理员三种角色注册 14 条工具定义），**按角色在服务端过滤可用工具**，且**不向模型暴露任何写操作与自由 SQL**，从架构上规避模型越权修改数据与 SQL 注入风险；构建 **20 条评测集**量化工具路由准确率，达 **20/20**；实现 LLM 不可用时的规则降级链路，降级后仍真实调用业务工具而非伪造结果。
- **工程化交付**：Maven 多环境配置（H2 开发 / MySQL 生产 profile 切换）、`docker-compose` 一键启动 MySQL + 应用、GitHub Actions CI 自动编译并运行 **8 个测试用例**、完整 README 与 API 文档。

## 三、把数字讲成故事：每一条怎么应对追问

面试官不会只看数字，他会挑一条往下问。**下面这些你必须真懂**，否则别写。

### 1. 「选课为什么用悲观锁，不用乐观锁？」

> 选课是**短事务 + 强一致**场景：一次请求只碰一行课程记录，事务里就几次读写，冲突概率高（热门课开选瞬间），而且业务上不能接受「用户点提交后被拒绝，需要重试」——学生体感很差。
>
> 乐观锁（版本号 + 失败重试）适合**读多写少、冲突低频**的场景，在这里会带来大量重试和失败提示。
>
> 所以我用了 `SELECT ... FOR UPDATE` 行锁：把并发放进数据库串行化，锁粒度只有一行，持锁时间极短（毫秒级），吞吐够用，而且天然没有超卖。
>
> 如果以后选课 QPS 上来了，正确的下一步是「Redis 预扣库存 + 异步落库」，或者给热门课做排队削峰，而不是继续加大行锁。

### 2. 「为什么不直接在 Java 里用 `synchronized`？」

> 那样只能保护单个 JVM。项目一旦多实例部署（或者以后上集群），`synchronized` 就完全失效了，仍然会超卖。
>
> 锁必须放在**共享资源所在的地方**，也就是数据库。所以我用数据库行锁，它的语义在多实例下依然正确。

### 3. 「N+1 是怎么发现的？122 条怎么算出来的？」

> 我在 SessionFactory 上挂了一个自定义的 `StatementInspector`，它会拦截每一条 Hibernate 发出的 SQL 并计数（ThreadLocal，避免并发串号）。
>
> 然后在基准接口里用 `reset()` / `count()` 夹住两种实现，就能拿到真实条数：
> 原实现是「1 条查学生 + 30 学生 × 4 作业 = 120 条 count」= **122 条**；
> 优化后用一条 `GROUP BY student_id` 一次性算出每个学生在多门作业上的提交数，加上查作业总数那条 = **2 条**。
>
> 关键是我没有只说「变快了」，而是让这个数字**可复现**：接口直接返回 naive / optimized 的对比，测试里也有断言。

### 4. 「为什么不让模型自由生成 SQL？」

> 因为那是把数据库的控制权交给了一个不可信的输出源。模型可以被提示词注入诱导，也可能自己写出 `DELETE` 或者跨权限查别人的数据。
>
> 我的做法是：模型只能从**预先定义好的工具**里选，每个工具是一段我写好、参数化、只读的业务逻辑；模型可以决定「调哪个工具、传什么参数」，但**不能决定执行什么 SQL**。
>
> 另外工具的可见性按角色在**服务端**过滤 —— 学生身份根本看不到教师工具，所以就算模型被诱导去调 `getCourseHomeworkStats`，也会被拒绝。这是权限边界，不依赖模型自觉。

### 5. 「工具只有 12 个，会不会路由错？」

> 会，所以我要量化它。我做了 20 条评测集：每条包含「用户问法 + 当前角色 + 期望调用的工具」，跑一遍算准确率。
>
> 评测集里我**故意加了容易混淆的用例**：比如「我的课程列表」在学生和教师下都要路由到同一个工具但参数不同；还有几条是「这个角色根本不该命中任何工具」——用来证明角色过滤真的生效，而不是靠关键词瞎猜。
>
> 当前准确率 20/20。但我要强调：这套评测集是我自己造的，所以它的意义不是「我的 Agent 很强」，而是「我建立了可迭代的评测方法」，以后换 prompt、换模型都能用它判断是变好还是变坏。

### 6. 「没有 API Key 的时候怎么办？」

> 我把降级链路当作一等公民来设计。没有 Key 时走规则路由（IntentRouter），它复用同一套工具注册表，所以**仍然会真实调用后端业务接口**，返回的仍然是数据库里的真数据 —— 只是「理解自然语言」的那部分换成了关键词匹配。
>
> 为什么这样设计：Agent 的核心价值是「能读到真实数据」，模型只是理解层。理解层可以降级，数据层不能伪造。
>
> 接口返回里会明确标 `mode: llm` 还是 `mode: fallback`，不掩盖。

### 7. 「token 存哪里？XSS 怎么办？」

**这条一定要老实回答，这是你的加分机会：**

> 我前端存在 `sessionStorage`，配合 `Authorization: Bearer` 头。这个方案对 XSS 是有风险的 —— 一旦页面被注入脚本，token 就能被读走。
>
> 更稳妥的是 `HttpOnly + Secure` 的 Cookie 配合 CSRF Token，那样 JS 读不到 token。
>
> 我当时选了 Bearer 方案是因为前后端分离时调试更方便、也更容易做多端复用；如果这个系统要上线，我会改成 HttpOnly Cookie，并且加上 CSP 头。**这是我明确知道的取舍，不是没想过。**

### 8. 「你原来的项目是 Swing 的，这个是什么关系？」

**不要撒谎。** 说：

> 原来那版是我大二的课设，Java Swing + 裸 JDBC，做的是同一个业务域。后来我发现它有两个问题：
> 一是桌面程序没法让人远程体验，二是代码里没有测试、没有构建工具、密码还是明文比对。
>
> 所以这次我把它重做成了 Web 版：业务模型沿用了（表结构、选课/作业/评分的数据关系都是我原来设计的），但架构换了 —— 引入了 Spring 生态、加了 JWT 认证、补了测试、修掉了原来的并发和性能问题。
>
> 对我来说这个过程比从零开始更有价值：**我知道每一处为什么要改。**

> ⚠️ 面试官如果问你原来那版代码，你要能说清 `selectCourse` 里那个 `FOR UPDATE` 是你自己写的（这是你原来代码里就有的、真正的东西）。

## 四、简历上放什么链接

**别放原来那个 surge 链接了**，或者至少不要把它当成「在线教育平台」的主演示。

按优先级：

1. **一个能点开的在线地址**（最重要）——见 `docs/DEPLOY.md`。国内建议租一台轻量云服务器（学生机一年几十块），配个域名 + HTTPS，链接就体面了。
2. **GitHub 仓库**（第二重要）——HR 不看代码，但会看**提交记录**和 **README 截图**。所以：
   - 不要一次性 push 90 个文件，要有**多个有意义的 commit**（feat/test/docs 分开）
   - README 顶部放三样东西：项目截图（或 GIF）、CI 徽章、Live Demo 链接
3. **一段 30 秒的录屏**：登录 → 看课程 → AI 助手提问并展开工具调用记录 → 性能基准面板。发在简历附件或 README 里。

**面试官点开链接后会看什么：**
- 能不能不注册就进去（→ 所以登录页必须列出演示账号）
- 按 F12 → Network 有没有真实请求（→ 现在有）
- 有没有一个「别人抄不走」的细节（→ 你有两个：并发超卖 0、N+1 从 122 条降到 2 条，而且是接口返回的真实数字）

## 五、诚实清单：这个项目现在的短板

面试官问到就直接承认，**主动交代比被问出来强得多**：

| 短板 | 怎么说 |
|---|---|
| 没有真实大模型 Key 的实测数据 | 「LLM 调用链路我是按 OpenAI 兼容协议实现的，本地没配 Key 时走 fallback；准确率 20/20 是规则路由的评测结果，换成真实模型后我会用同一套评测集重新跑一遍对比。」 |
| 没有 Redis / 消息队列 / 分布式 | 「单机 MySQL 的选课并发已经验证没问题；数据量和 QPS 上去之后我会引入 Redis 预扣库存和缓存，这是明确的下一步。」 |
| 没有微服务 | 「7 个业务域在一个进程里，边界清晰但确实不需要拆。硬拆成微服务只会增加运维成本，我不觉得现在拆是对的。」 |
| 没有真实用户量和压测报告 | 「并发数据来自我自己写压测接口，不是生产数据。」切别说「支撑了多少用户」这种编造的话。 |
| 部署在单机 | 「Docker Compose 单机部署。上生产要加 Nginx 反向代理、HTTPS、数据库主从和监控。」 |

**绝对不要做的事**：编造用户量、并发量、QPS、上线时间。面试官很容易用一个具体问题戳穿，一旦被戳穿，整个简历都不可信了。
